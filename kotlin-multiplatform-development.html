Kotlin Multiplatform

Share the logic. Keep the interface native.

Kotlin Multiplatform gives you one codebase for the rules that must never differ between platforms, and two interfaces that each feel like they belong.

Short answer

Kotlin Multiplatform (KMP) shares business logic across Android and iOS while the interface stays fully native on each platform. Networking, data models, local storage, sync, and validation are written once in Kotlin and compiled to a native binary on iOS. The interface is built in Jetpack Compose on Android and SwiftUI on iOS.

Unlike Flutter or React Native, there is no shared UI layer and no runtime bridge. Building for both platforms with KMP typically costs 35 to 55 percent more than Android alone, not double, and KMP can be adopted one module at a time inside an app that already exists.

What is shared, and what is not.

The dividing line matters more than the technology. Everything that represents a business rule is shared. Everything a user touches is native.

Written once, in Kotlin

  • Data models and the domain layer
  • API clients and serialisation, typically with Ktor
  • Local database and caching, typically with SQLDelight
  • Offline sync and conflict resolution
  • Validation, permissions logic, and pricing or scheduling rules
  • Analytics events, so both platforms report identically

Written natively, per platform

  • The interface: Jetpack Compose on Android, SwiftUI on iOS
  • Navigation and platform conventions
  • Permissions dialogs, notifications, and background execution
  • Anything using a platform capability that has no shared equivalent

On a data-driven product that split usually puts 40 to 60 percent of the codebase in shared Kotlin. The number is lower for a visually elaborate consumer app and higher for an operational tool where most of the complexity is rules rather than pixels.

KMP, Flutter, and React Native compared.

These three are often presented as competitors solving the same problem. They are not. Flutter and React Native share the interface; KMP deliberately does not.

There is no universally correct answer here. The right choice depends on whether the interface or the logic carries most of your product's complexity, and on what your team can maintain after the studio hands over.

When KMP is the wrong choice.

A studio that recommends the same technology for every project is selling a preference, not advice. KMP is a poor fit when:

  • The product is Android-only with no real iOS plan. You pay the structural cost of sharing and never collect the benefit.
  • The app is mostly screens over a simple API and your team already ships confidently in Flutter or React Native.
  • The interface is the product. Highly visual consumer apps spend most of their budget on the layer KMP does not share.
  • Nobody on the receiving team writes Kotlin. Handover matters more than architectural elegance.

In those cases AppVion will say so during the Product Clarity Sprint, which is a great deal cheaper than discovering it in month three.

Kotlin Multiplatform questions, answered directly.

What is Kotlin Multiplatform?

Kotlin Multiplatform, usually shortened to KMP, is a JetBrains technology that lets one Kotlin codebase share business logic, data models, networking, and local storage across Android, iOS, desktop, and web, while the user interface is written natively on each platform. It is not a cross-platform UI framework. The shared code compiles to a native binary on iOS rather than running through an interpreter or bridge.

How is KMP different from Flutter or React Native?

Flutter and React Native share the interface as well as the logic, and draw or bridge their own components. KMP shares only the logic and leaves the interface fully native: Jetpack Compose on Android, SwiftUI on iOS. That means the app looks and behaves exactly like a platform app, at the cost of building the interface twice. KMP is also incremental: you can share a single module inside an existing native app rather than committing to a rewrite.

What exactly gets shared in a KMP project?

Typically the business rules, data models, API clients, local database, caching and sync logic, validation, and analytics. That is usually 40 to 60 percent of the codebase on a data-driven product. What stays native is the interface, navigation, platform permissions, and anything touching a platform-specific capability.

Does KMP cost less than building two separate apps?

Yes, but not half. Building the same product for Android and iOS with KMP typically costs 35 to 55 percent more than Android alone, rather than 100 percent more, because the logic is written once and only the interface is rebuilt. The larger saving arrives later: a business rule changes in one place instead of two, and the two apps cannot silently drift apart.

Is Kotlin Multiplatform production-ready?

Yes. KMP reached stable status for sharing business logic and is used in production by large engineering organisations. The shared code is compiled ahead of time to a native framework on iOS, so there is no runtime bridge to debug. Compose Multiplatform for shared UI is a separate and less mature choice, and AppVion generally recommends keeping the interface native.

When is KMP the wrong choice?

When the app is Android-only with no credible iOS plan, KMP adds structure you will never cash in. When the product is mostly screens over a simple API and the team is already fluent in Flutter or React Native, those will ship faster. And when a team has no Kotlin experience at all, the learning curve is real.

Can KMP be added to an existing app?

Yes, and that is often the best way to adopt it. A single module — the API client, or the offline cache — can be extracted into shared Kotlin and consumed by the existing Android and iOS apps without either being rewritten. It is one of the few architectural migrations that can be done in slices.
