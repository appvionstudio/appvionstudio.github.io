Case study · Property management

One repair, four people, no phone calls.

A tenant reports a leak, a property manager assigns it, a contractor fixes and evidences it, and the manager closes it. ProFix is that loop, with the business rules written once and shared across platforms.

In short

ProFix is a Kotlin Multiplatform property management SaaS. Four roles use it: the platform owner, property managers, contractors, and tenants. A tenant raises a complaint against their unit, a manager turns it into a work order and assigns a contractor from an invite-only directory, the contractor updates status and attaches evidence, and the manager approves remotely.

Because it is built on Kotlin Multiplatform, the rules that must never differ — who can see what, when a work order may close, how plan limits apply — are written once in shared Kotlin rather than twice in two languages that quietly drift apart.

Why property maintenance goes wrong.

A property manager sits between people who never speak to each other. Tenants report problems by phone, text and in person. Contractors are booked by whoever was reachable. Evidence that work happened arrives as a photo in a WhatsApp thread, if at all. Invoices arrive weeks later against jobs nobody can now identify.

The failure is not that any single step is hard. It is that the record of what happened is spread across four people's phones, so closing a job means reconstructing it from memory.

Decisions that shaped it.

Kotlin Multiplatform, with the interface left native

The shared module holds the domain models, repository interfaces, sync engine and the rules governing who may do what. That is the code where a difference between Android and iOS becomes a bug someone finds in production. The interface stays native on each platform, so nothing has to pretend to be a platform it is not.

Plan limits enforced by database trigger, not by hiding buttons

The free tier allows three properties, twenty work orders and three contractors. Those ceilings are migrations in Postgres, so they hold regardless of which client is talking to the API. A limit implemented in the interface is a suggestion; a limit implemented as a constraint is a limit.

Contractors and tenants join by invite, never by open signup

A property manager generates an invite code from settings. A contractor signs up and enters it; a tenant signs up and enters a code that links them to a specific unit. Nobody lands inside a manager's portfolio by guessing an email domain, and the manager can see exactly who they let in.

Offline-first, because maintenance happens in basements

SQLDelight holds a local copy and the sync engine reconciles on reconnect. A contractor in a plant room with no signal can still update a job, and the update lands when the phone comes back rather than being lost with a spinner.

What changes for a property manager.

  • One record per job, not four. The complaint, the assignment, the evidence and the approval are the same object, so closing a job is reading it.
  • Approval stops requiring a site visit. The manager sees the evidence attached to the job and approves from wherever they are.
  • The contractor directory is curated, not accidental. Skills and availability sit against real people the manager invited.
  • Tenants stop chasing. A tenant who can see the status of their own complaint does not phone to ask about it, which removes the single largest interruption from a manager's day.
  • Growth is priced honestly. A three-property landlord uses it free. A management company with a real portfolio pays for the volume it uses, and the ceiling is enforced where it cannot be argued with.

Before release the product was taken through a documented 56-case test plan covering every role, plus a dedicated Play Store launch hardening pass.
